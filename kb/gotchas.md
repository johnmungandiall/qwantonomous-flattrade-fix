# Gotchas — traps specific to this repo. Read before editing.

- ZeroMQ Port 5555 bind conflicts in `websocket_proxy/server.py#WebSocketProxy.__init__`: The proxy SUB socket binds `ZMQ_HOST:ZMQ_PORT` (port 5555). Running multiple OpenAlgo instances or rapid restarts without port release causes `ZMQError: Address in use`. Use `is_port_in_use` with a grace wait window.
- Flattrade WebSocket Auth Timing in `broker/flattrade/streaming/flattrade_websocket.py#FlattradeWebSocket._on_open`: Subscribing before server returns `AUTH_SUCCESS` causes Flattrade to send a close frame (`opcode=8`). `on_open` and resubscribe callbacks must only fire inside `_handle_auth_response` after authentication succeeds.
- Flattrade Single WS Connection Limit in `services/order_update_service.py#_POLLING_BROKERS`: Flattrade allows only 1 active WebSocket connection per user ID. Running a dedicated order-update WS evicts the market-data WS (and vice versa) with opcode 8. Flattrade must use polling for order updates.
- Frontend WebSocket Auto-Reconnect in `frontend/src/lib/MarketDataManager.ts#MarketDataManager`: Do not gate reconnects on `!event.wasClean`, as server close frames (ping timeout, idle close) mark `wasClean=true` and would otherwise permanently stall auto-reconnect.
- **LOCAL PATCH (2026-10-22, commit 24161aa) — a flat PositionBook crashed the square-off into HTTP 500.** `broker/flattrade/api/order_api.py#close_all_positions` used to do `if positions_response is None or positions_response[0]["stat"] == "Not_Ok"`, assuming the `PositionBook` reply is always a non-empty LIST. A flat account can answer with `None`, an empty list, or a bare `{"stat":"Not_Ok","emsg":...}` DICT (the shape [[../docs/-api-references/02-orders]] records for PositionBook failures — in the Qwantonomous-Engine repo), so `[0]` raised `KeyError: 0` / `IndexError`. `services/close_position_service.py#close_position_with_auth` catches everything and returns HTTP 500 *"Failed to close positions due to internal error"*, so a genuinely FLAT account looked like a FAILED close: callers retried 3x and a client's P.Cross side switch stayed held. The guard now normalises all those shapes to the documented "No Open Positions Found" / 200, and only then iterates real rows. Same `[0]` defect still exists in `broker/shoonya/api/order_api.py#close_all_positions` and `broker/zebu/api/order_api.py#close_all_positions` (not patched — different brokers); `broker/tradesmart` has the guard but returns a FALSE "All Open Positions SquaredOff" when the book is unreadable. **This is a LOCAL patch to a vendored upstream app — an OpenAlgo upgrade will overwrite it; re-check after any upgrade.**
- **LOCAL PATCH (2026-10-22, commit 4d662f5) — a FAILED OrderBook read crashed cancel-all into HTTP 500.** `broker/flattrade/api/order_api.py#cancel_all_orders_api` iterated `get_order_book()`'s reply and called `order.get("status")` per item. A failed read returns a bare `{"stat":"Not_Ok","emsg":...}` DICT, so iterating yielded its string KEYS and `.get` raised `AttributeError: 'str' object has no attribute 'get'`; `services/cancel_all_order_service.py#cancel_all_orders_with_auth` turns any exception into HTTP 500 *"Failed to cancel all orders due to internal error"*, even with nothing pending. Now guarded on list type + per-item dict, returning the existing empty result. **Rule: never iterate or index a broker helper's reply before type-checking it — the error object is not the documented list** (same family as the PositionBook bug above). Live evidence: `errors.jsonl` 2026-10-21 09:15:00. Client-side it was NON-fatal (the app logs it and still squares off), so cosmetic, not dangerous.
  Full write-up for BOTH flattrade patches (live tracebacks from `log/errors.jsonl`, before/after behaviour matrices, cross-broker audit): `docs/2026-10-22-flattrade-squareoff-cancelall-fixes.md`.

- **FIXED (2026-10-25) — `npm run build` used to fail on the retired `'strategy'` toast category, so `frontend/dist` was never written.** `frontend/src/pages/strategy/{ConfigureSymbols,NewStrategy,StrategyIndex,ViewStrategy}.tsx` called `showToast.*(..., 'strategy')` although the `strategy` key was RETIRED from `AlertCategories` in `frontend/src/stores/alertStore.ts` — 30 × `TS2345`. The argument is now simply omitted (matching the live pages `List`/`Wizard`/`Detail`/`Edit`, which never passed a category), and the unused `event` parameter on the `socket.onclose` handler in `frontend/src/lib/MarketDataManager.ts#MarketDataManager` was dropped (`TS6133`). `tsc -p tsconfig.app.json --noEmit` is now clean. **Rule: `frontend/package.json` builds with `tsc -b && vite build`, so ANY type error stops vite and the UI silently ages — run the build, never assume it.**
- **`frontend/dist` IS now committed and must stay committed — every branch/tag zip must run without `npm`.** `.gitignore` used to ignore `frontend/dist/` (blanket `dist/` + an explicit line), so a GitHub source archive of any branch whose CI never ran the `commit-dist` job had no UI at all. The blanket rule is now negated with `!frontend/dist/` and the explicit rule is gone; `.dockerignore` already carried `!frontend/dist/`. **Do not re-add a `frontend/dist` ignore, and re-run `npm run build` + `git add frontend/dist` after any frontend change** — a stale dist is served immutably for a year, so only content-hashed filenames save it.

- **Missing `frontend/dist` is a SUPPORTED state — keep the error path tuple-free.** `app.py#create_app` registers `react_bp` only when `blueprints/react_app.py#is_react_frontend_available` is True, so without a build the SPA routes do not exist at all. `serve_react_app` therefore returns a real `make_response(..., 503)` Response, never a bare `(html, status)` tuple: the 404 handler pairs it (`return serve_react_app(), 404`), and a tuple inside that pair nests into `((html, 503), 404)` → Flask's *"did not return a valid response … but it was a tuple"* TypeError raised **from inside** an error handler → `app.py#internal_server_error` → `redirect("/error")` → 404 again. That loop is what produced ERR_TOO_MANY_REDIRECTS. The 500 handler now redirects only when a build exists AND the request is not already on `/error`; `app.py#method_not_allowed_error` and the GET branch of `blueprints/auth.py#login` answer `serve_react_app()` instead of redirecting to a React-only path (`GET /setup` is POST-only in `blueprints/core.py#setup`, so that redirect ended on a bare 405). **Rule: an error handler must never redirect to a path that may not be registered.**

- **A hand-edited `.env` with one non-UTF-8 byte used to break the startup version check.** `utils/env_check.py#check_env_version_compatibility` read `.env` and `.sample.env` with the platform default encoding, which is cp1252 on Windows, so a 0x9d byte raised `'charmap' codec can't decode byte 0x9d` and printed *"Warning: Could not read .env file"* on every boot (the check then silently answered "compatible"). Both reads now pass `encoding="utf-8", errors="replace"` — safe because only the ASCII `ENV_CONFIG_VERSION` key name is parsed. **Rule: every `.env` read states its encoding; the platform default is not UTF-8 on Windows.**

Cite the code that proves each trap as `path#symbol` so [[conventions]] checks pass.
